# Docker and Docker Compose — Actual Project Steps

## Project

**Electricity Billing Application**

Repository branch:

```text
main
```

This document records the actual Docker and Docker Compose steps implemented in the Electricity Billing DevOps project.

---

# 1. Why Docker Was Added

The application is a Spring Boot application connected to MySQL.

Initially, the application ran directly on the local machine:

```text
Spring Boot Application
        |
        v
     MySQL
```

Docker was introduced so that the application could run in a reproducible containerized environment.

The main goals were:

* Package the Spring Boot application into a Docker image.
* Run the application inside a container.
* Run MySQL inside a container.
* Connect the application container to the MySQL container.
* Persist MySQL data using a Docker volume.
* Manage both containers using Docker Compose.
* Handle service startup dependencies correctly.
* Keep database credentials out of GitHub.

Docker Compose is designed to define and run multi-container applications from a YAML configuration.

# 2. Dockerfile

A `Dockerfile` was created in the project root.

```dockerfile
FROM eclipse-temurin:17-jre

WORKDIR /app

COPY target/electricity-billing-*.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]
```

## Explanation

### FROM

```dockerfile
FROM eclipse-temurin:17-jre
```

Uses a Java 17 JRE base image.

The application only needs the Java runtime to execute the packaged JAR.

### WORKDIR

```dockerfile
WORKDIR /app
```

Sets `/app` as the working directory inside the container.

### COPY

```dockerfile
COPY target/electricity-billing-*.jar app.jar
```

Copies the Spring Boot JAR generated by Maven into the container.

### ENTRYPOINT

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
```

Starts the Spring Boot application when the container starts.

# 6. First Database Connectivity Problem

The application container initially failed to connect to MySQL.

The reason was that the application was running inside Docker while MySQL was still running directly on Windows.

Inside the container:

```text
localhost
```

means:

```text
the application container itself
```

It does not mean the Windows host.

The application therefore needed a different database host when running inside Docker.

The application configuration was changed to use environment variables:

```properties
spring.datasource.url=jdbc:mysql://${DB_HOST:localhost}:${DB_PORT:3306}/${DB_NAME:electricity_billing}
spring.datasource.username=${DB_USER:root}
spring.datasource.password=${DB_PASSWORD}
```

This allowed the database host to be changed depending on the environment without modifying the source code.

# 7. Why Docker Compose Was Introduced

Running the application and database separately became inconvenient.

The desired architecture was:

```text
+---------------------------+
| Docker Compose            |
|                           |
|  +---------------------+  |
|  | Spring Boot App     |  |
|  | Port 8081           |  |
|  +----------+----------+  |
|             |             |
|             | Docker      |
|             | network     |
|             v             |
|  +---------------------+  |
|  | MySQL 8             |  |
|  | Port 3306            |  |
|  +---------------------+  |
|             |             |
|             v             |
|       mysql-data         |
|       volume             |
+---------------------------+
```

Docker Compose allows both services to be defined and managed together. The standard `docker compose` command provides commands such as `up`, `ps`, `logs`, `down`, and `config`.

# 8. Docker Compose Configuration

The project uses `docker-compose.yml`.

The main services are:

```yaml
services:

  app:
    image: electricity-billing:1.0

    ports:
      - "8081:8081"

    environment:
      DB_HOST: mysql
      DB_PORT: 3306
      DB_NAME: electricity_billing
      DB_USER: root
      DB_PASSWORD: ${DB_PASSWORD}

    depends_on:
      mysql:
        condition: service_healthy

  mysql:
    image: mysql:8.0

    environment:
      MYSQL_DATABASE: electricity_billing
      MYSQL_ROOT_PASSWORD: ${DB_PASSWORD}

    volumes:
      - mysql-data:/var/lib/mysql

    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-p${DB_PASSWORD}"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:

  mysql-data:
```

# 10. Docker Service-to-Service Communication

The application uses:

```yaml

```

The important point is that:

```text
mysql
```

is the Compose service name.

Therefore, inside the Docker Compose network:

```text
Spring Boot
    |
    | mysql:3306
    v
MySQL
```

The application does not use:

```text
localhost:3306
```

to reach the MySQL container.

# 12. Docker Volume

The Compose configuration contains:

```yaml
volumes:
  - mysql-data:/var/lib/mysql
```

MySQL stores its database files under:

```text
/var/lib/mysql
```

inside the MySQL container.

The named Docker volume:

```text
mysql-data
```

is mounted at that location.

Therefore:

```text
Docker Volume
mysql-data
     |
     v
/var/lib/mysql
     |
     v
MySQL database files
```

The purpose is to keep database data independent from the lifecycle of the MySQL container.

# 13. The Startup Timing Problem

The first version used:

```yaml
depends_on:
  - mysql
```

The application sometimes failed during startup.

The application logs contained an exception chain similar to:

```text
Failed to execute database script
        |
        v
CannotGetJdbcConnectionException
        |
        v
Communications link failure
        |
        v
java.net.ConnectException: Connection refused
```

The MySQL logs showed that MySQL was still initializing.

Eventually MySQL reported:

```text
MySQL init process done. Ready for start up.
```

and:

```text
mysqld: ready for connections.
port: 3306
```

## Root cause

The problem was a startup timing/readiness issue.

The sequence was:

```text
MySQL container starts
        |
        v
MySQL still initializing
        |
        v
Spring Boot starts
        |
        v
Spring Boot attempts MySQL connection
        |
        v
MySQL is not ready
        |
        v
Connection refused
```

The problem was not incorrect MySQL configuration.

The application simply attempted to connect too early.

---

# 14. Health Check Solution

A MySQL health check was added:

```yaml
healthcheck:
  test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-p${DB_PASSWORD}"]
  interval: 5s
  timeout: 5s
  retries: 10
```

The application dependency was changed to:

```yaml
depends_on:
  mysql:
    condition: service_healthy
```

The resulting startup sequence is:

```text
Start MySQL
     |
     v
MySQL initializes
     |
     v
Health check
     |
     +---- Not healthy ----> Wait
     |
     v
Healthy
     |
     v
Start Spring Boot
     |
     v
Connect to MySQL
```

This resolved the startup problem.

# 16. Troubleshooting Docker Logs

When the application failed, the container logs were inspected using:

```cmd
docker logs <container-name>
```

For Compose services:

```cmd
docker compose logs app
```

and:

```cmd
docker compose logs mysql
```

For large logs, useful techniques include:

```cmd
docker logs --tail 50 <container-name>
```

Search for errors:

```cmd
docker logs <container-name> 2>&1 | findstr /I "ERROR"
```

Search for exceptions:

```cmd
docker logs <container-name> 2>&1 | findstr /I "Exception"
```

Search for nested Java exception causes:

```cmd
docker logs <container-name> 2>&1 | findstr /I "Caused by"
```

Search for a specific message:

```cmd
docker logs <container-name> 2>&1 | findstr /I "Connection refused"
```

For Java/Spring applications, following the `Caused by:` chain is particularly useful for identifying the underlying cause of a large stack trace.

# 18. Database Password Security

Initially, the database password was directly present in the Compose file.

This was identified as a security problem because the repository is public.

The password was moved to a local `.env` file.

The Compose configuration now uses:

```yaml
DB_PASSWORD: ${DB_PASSWORD}
```

and:

```yaml
MYSQL_ROOT_PASSWORD: ${DB_PASSWORD}
```

The local `.env` contains the actual password:

```text
DB_PASSWORD=<actual-password>
```

The `.env` file is excluded through `.gitignore`:

```text
### DATABASE RELATED ###

.env
```

Therefore:

```text
Local machine
     |
     +-- .env
     |     |
     |     +-- actual password
     |
     +-- docker-compose.yml
           |
           +-- ${DB_PASSWORD}
```

GitHub receives:

```text
docker-compose.yml
```

but does not receive:

```text
.env
```

This prevents the actual database password from being committed to the repository.

# 24. Important Interview Points

### Why Docker?

> Docker packages the application and its runtime dependencies into a reproducible container environment.

### Why Docker Compose?

> Docker Compose allows multiple related services, such as the application and database, to be defined and managed together.

### Why use `mysql` instead of `localhost`?

> Within the Compose network, services can communicate using their service names. The application therefore connects to MySQL using `mysql:3306`.

### Why use a volume?

> The volume keeps MySQL data separate from the container lifecycle so database data can persist when the container is recreated.

### Why use a health check?

> Container startup does not necessarily mean that the application inside the container is ready to accept connections. The health check verifies MySQL readiness before the application starts.

### Why not hardcode the password?

> Credentials should not be committed to source control. Environment variables and ignored local configuration are used to keep secrets outside the Git repository.

### What was the Docker Compose issue?

> The Spring Boot application started before MySQL was ready to accept connections, resulting in a `Connection refused` error. A MySQL health check and `depends_on` with `condition: service_healthy` were added to solve the readiness problem.
